What is this project?

A self-improving attack detector that runs entirely on your laptop. It generates fake cloud attack events, tests whether the current detector can catch them, retrains itself on what it saw, and keeps score — all without touching any real AWS account, credentials, or the internet.

One-line pitch: Traditional detectors are written once and go stale. Purple Loop writes itself, governed by rules that prevent it making things worse.

The "purple" in the name is standard security language: red team attacks, blue team defends, purple team does both at once in a loop.

One round, step by step

The order is enforced in code — steps 3 and 4 cannot be swapped.

1
Pick a variant

The policy looks at past misses and picks an attack style the detector has struggled with. First 2 rounds explore freely.

2
Generate events

Synthetic CloudTrail-shaped records for that variant, plus fresh benign traffic for the same simulated day.

3
Score held-out critical

Run the current model against this brand-new variant. Measurement happens before it enters training. The harness raises an exception if you try to cheat.

4
Append to corpus

Only now does the variant enter the training set. Corpus is append-only — no round can be modified later.

5
Retrain

A fresh RandomForest is trained on the entire corpus — all rounds so far, all families.

6
Recalibrate threshold

Set the alert cutoff at the highest value that keeps benign FPR ≤ 1%.

7
Regression suite

Run the candidate on all previously seen variants. Did we forget anything we used to catch?

8
Gate governance

Promote only if recall didn't drop AND false positives didn't rise on an identical fresh sample. Otherwise log a reject and keep the old model.

9
Update policy

Attribute misses to their knob value. Update the smoothed miss-rate table so round N+1 targets the right weakness.

3 attack families

4 mutation knobs — what the attacker changes

The technique (which APIs, which buckets) stays the same. What changes is how the attack is delivered to evade the detector.

KnobValuesWhat the attacker is doing
delay_profileburst / fast / spaced / slow / jitteredSlow down or randomise timing so it doesn't look automated
batch_sizesmall / medium / largeBreak the attack into fewer or more API calls per chunk
call_ordercanonical / reversed / interleaved / splitMix attack calls with innocent filler or do them out of expected order
identity_reusesingle / two_identities / per_call_identityUse different AWS identities per call so no one identity looks suspicious

540 possible combinations across 3 families × 4 knobs. A 20-round run visits 20 of them — plus the 6 hand-authored seed variants = 26 total seen.

Hard negatives — why the 1% FPR actually means something

If benign traffic looks nothing like attacks, any detector scores 0% FPR trivially. These four benign types are designed to look like attacks along one axis:

Likely questions during the demo

Why don't you use real AWS data?

Two reasons. First, real CloudTrail logs contain PII and credentials — we can't share them in a demo or a repo. Second, synthetic data lets us control exactly what attack variants exist and measure generalization precisely. The events are shaped exactly like CloudTrail records (same field names, same API call vocabulary), so the feature engineering transfers.

How do you know the detector isn't cheating?

Two mechanisms. First, features never include raw event names or variant_id — the extractor only computes statistics (counts, timing, fractions). Second, heldout_eval() in harness/heldout.py calls assert_unseen() which raises an AssertionError if the variant is already in the corpus. It's not a warning — it crashes. And test_no_leakage.py tests this assertion directly.

What is the FPR budget and why 1%?

FPR = false positive rate = the fraction of innocent sessions that get flagged as attacks. 1% means: for every 100 normal employees doing normal work, at most 1 gets a false alert. That's a standard SOC threshold — above ~2% and analysts start ignoring alerts entirely. The budget is enforced in two ways: threshold calibration sets the cutoff so benign FPR ≤ 1%, and the gate rejects any candidate whose FPR exceeds budget even if its recall is perfect.

The curve saturates after one round — is that a failure?

It's an honest result, not a failure. It means the synthetic attack distribution is separable from benign traffic from session shape alone — the timing and ordering mutations aren't enough to fool the detector once it has one slow-timing example. We documented this upfront in docs/RESULTS.md and listed four concrete changes that would make the task harder: overlapping benign traffic on all axes, quieter attacks, smaller seed corpus, per-family curves. The loop machinery is correct; the detection problem is too easy to show a gradual climb.

What is the ablation and what did it find?

We ran the same loop three times with different feature subsets: all 67 features, delivery-only (32 timing/ordering features), and technique-only (35 semantic features: admin grants, log narrowing, sensitive reads). The hypothesis was that technique features are what drive generalization. Result: delivery-only scored 0.896 vs 0.906 for the full set — a 0.010 gap — so the claim is not supported. Timing and ordering features alone generalise almost as well. We left that result standing rather than re-partitioning features until it flipped.

What is the adaptive policy actually doing?

After each round, it looks at which sessions were missed and records which knob values appeared in those misses. It computes a smoothed miss rate per knob value (using shrinkage — so one noisy round can't dominate) and biases the next variant generation toward the weakest value. For example: round 1 missed delay=slow at 100%. Policy pinned to delay=slow for several rounds. Once the detector caught those variants reliably, the miss rate fell and the policy moved on to the next weakness.

Why can't you just push --force to fix a bad model?

The registry is designed to make that impossible silently. Every candidate gets a row; the only write is INSERT, never UPDATE or DELETE. To "revert", you flip the promoted flag on a previous row — but the bad candidate's row stays in the audit trail with its reason. The governance gate exists precisely because a model can have better recall and worse FPR at the same time; without a gate, the loop would auto-upgrade to a noisier detector.

Could this work on real CloudTrail logs?

The feature engineering would transfer directly — same field names, same API vocabulary. The main differences: real logs have class imbalance (attacks are rare), real benign traffic is far more diverse, and real attackers don't come from a known knob space. So the generalisation claim would need re-validation. The loop architecture (held-out scoring, governed promotion, append-only corpus, adaptive policy) is equally applicable to real data. The four changes in docs/RESULTS.md §6 are also the right steps toward real-data readiness.

Honest limitations — say these first

  • Synthetic events. Shaped like CloudTrail but generated in-process. No claim transfers to real logs without re-validation.
  • Curve saturates. One early miss followed by 19 clean rounds is not a gradual learning curve with 20 informative points.
  • Ablation negative. Delivery-only features score nearly as well as the full set — the technique features are not proven to be what drives generalization.
  • Session-level detection. One session_id = one episode. A real attacker spreading activity across sessions and days needs a different unit of analysis.
  • Sensitivity is declared, not learned. The feature extractor knows which buckets are sensitive from a lexicon. Realistic, but it's domain knowledge handed to the model.
  • 20 rounds, single seed. No confidence intervals. One run is enough to show the mechanism, not enough to make the trend statistically meaningful.

Finishing on real limitations is stronger than overclaiming. The loop is autonomous, the measurement is honest, false positives stayed inside budget, and the self-updating is governed. That's what this run establishes.
